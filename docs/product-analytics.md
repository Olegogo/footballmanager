# Измерение пользы через Umami

События отправляются в существующий сайт Umami из miniapp. Схема использует
[track(name, data) и identify(id)](https://docs.umami.is/docs/tracker-functions).
Локальные/dev-запуски не отправляют продуктовые события. Медленный трекер
обслуживается ограниченной очередью в памяти; блокировка аналитики не мешает приложению.

## События

| Событие | Когда считается |
| --- | --- |
| app_open | Приложение успешно получило начальные данные, один раз на загрузку |
| auth_success | Авторизованный вход, включая восстановленную сессию; method различает telegram, telegram_web, session |
| auth_required | Пользователь попытался совершить действие, но авторизоваться не удалось |
| screen_view | Изменился экран; перерисовки и автообновление не увеличивают счетчик |
| game_view | Открыты детали игры, включая прямую ссылку |
| games_empty | Показан пустой список, один раз на фильтр за загрузку |
| create_game | Сервер успешно создал новую игру; редактирование не считается |
| join_requested | Сервер принял новую заявку; повторное нажатие из pending/participant не считается |
| join_cancelled | Успешная отмена заявки, actor=self/organizer |
| join_approved | Организатор успешно одобрил заявку; событие принадлежит организатору |
| invite_accepted | Участник успешно принял приглашение |
| invite_declined | Участник успешно отклонил приглашение |
| rating_available | На экране игры пользователю доступно оценивание |
| rating_saved | Сервер сохранил оценку; rating_mode=quick/detailed, mode=first/update |
| rating_completed | Первая непустая оценка пользователя в игре; это не оценка всего состава |
| profile_saved | Сохранена форма личной карточки |

Общие поля: source=telegram/web, authenticated. События игры содержат game_id,
game_status и join_status. Все идентификаторы игр внутренние. Случайный UUID для
аналитики сохраняется у игрока, возвращается только самому авторизованному игроку
и передается в identify для объединения визитов. Имена, usernames, Telegram ID,
токены, поисковые запросы, адреса и поля форм в события не передаются.

## Отчеты в Umami

1. Активация за визит: app_open → auth_success → game_view → join_requested.
   Отдельная ветка приглашений: app_open → game_view → invite_accepted.
2. Оценивание: rating_available → rating_completed. Для количества изменений
   использовать rating_saved с mode=update. Считать уникальных пользователей,
   а для метрики на матч — уникальные пары пользователя и game_id.
3. Возвраты: сравнивать пользователей с app_open в разные недели; отдельно
   смотреть пользователей с join_requested/invite_accepted для разных game_id.
   Это повторное участие в сценарии записи, не подтвержденная явка.
4. Точки потерь: games_empty по filter; auth_required по screen; доля отмен
   join_cancelled с actor=self относительно заявок.

Заявка, одобрение и оценивание происходят в разные дни и иногда у разных людей:
не объединять их в одну воронку одного визита. join_approved принадлежит организатору,
поэтому не считать его действием участника. События кнопок Telegram-бота и
фактическая явка этой браузерной схемой не измеряются. Старые периоды не заполняются.
Блокировщики и закрытие приложения до доставки могут привести к недоучету.

## Проверка и запуск

`node --test tests/analytics.test.js tests/analytics-actions.test.js`

После публикации открыть miniapp, выполнить действие тестовым аккаунтом и проверить
событие и его поля в Umami. Отчеты выше нужно создать в панели Umami: код только
отправляет события и не меняет настройки кабинета. Не отправлять синтетические
успешные события в рабочую аналитику для тестирования.
